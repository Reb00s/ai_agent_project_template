# SDD через OpenSpec — обязательный цикл задачи

OpenSpec включается для проекта только после подтверждения пользователя.
Plane остаётся источником задач и статусов; OpenSpec — источником требований
и истории изменений поведения. Спецификации хранятся в git вместе с кодом.

## Подключение и установка

1. При инициализации проекта и подключении Plane агент спрашивает:
   «Использовать OpenSpec для разработки через спецификации?».
2. Если ответ «да» и CLI отсутствует, агент устанавливает его один раз на
   машину агента по официальной инструкции:
   `curl -fsSL https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/scripts/binary/install.sh | sh`.
   Для каждого следующего проекта повторная установка не нужна.
3. Проверка: `openspec --version`, затем рабочий вызов `openspec list --json`.
   Если standalone-сборка не работает, используется поддерживаемый npm-вариант
   `npm install -g @fission-ai/openspec` (Node.js 20.19+). Нельзя считать
   установку завершённой только по выводу версии. Если `~/.local/bin` не в
   `PATH`, агенты вызывают CLI по абсолютному пути `~/.local/bin/openspec`.
4. В корне репозитория приложения выполняется:
   `openspec init <project_root> --tools kimi --no-animation --no-copilot-cloud`.
   Появляются `openspec/specs/`, `openspec/changes/` и навыки Kimi Code.
   После обновления CLI интеграции обновляются через `openspec update`.
5. В локальном `~/.kimi-code/plane_agents.json` сохраняются
   `openspec_enabled: true` и `project_root`. Файл не коммитится.
   Если пользователь отказался — `openspec_enabled: false`, задачи идут без
   обязательного SDD-цикла.

## Цикл каждой задачи

Идентификатор изменения: `<plane-id>-<краткое-имя>` в kebab-case, например
`dangerweb-22-pagination`. Один issue = один активный change, включая все
доработки. Новый агент продолжает существующий change и не создаёт дубликат.

1. **Контекст.** Субагент читает issue, комментарии, `openspec/specs/` и
   существующий change. При неясных требованиях сначала исследует код по
   алгоритму `openspec-explore`, не меняя его.
2. **Предложение.** По алгоритму `openspec-propose` создаётся change:
   `openspec new change <change-id> --json`. Обязательные артефакты:
   - `proposal.md` — цель, причина, рамки, что не входит;
   - `specs/<capability>/spec.md` — ADDED/MODIFIED/REMOVED Requirements
     и сценарии Given/When/Then;
   - `design.md` — техническое решение и последствия, если оно нетривиально;
   - `tasks.md` — шаги реализации и проверки с чекбоксами.
   Для изменений без изменения поведения в `.openspec.yaml` указывается
   `skip_specs: true`; для UI и бизнес-логики это не применяется.
3. **Валидация до кода.** `openspec validate <change-id> --strict --json` и
   `openspec status --change <change-id> --json`. Пока структура невалидна
   или планирование не завершено, код менять запрещено. Путь к change
   добавляется в комментарий Plane.
4. **Реализация.** Субагент читает
   `openspec instructions apply --change <change-id> --json`, выполняет
   `tasks.md`, отмечает только реально сделанные пункты `[x]`, запускает
   тесты и проверяет контур. Если решение меняется, сначала обновляются
   артефакты change, затем код.
5. **Доработка.** Прежний агент читает новые замечания, обновляет тот же
   proposal/spec/design/tasks по алгоритму `openspec-update-change`, снова
   выполняет strict-валидацию и только затем меняет код.
6. **Сдача.** Перед «Задача на тестировании» повторяются strict-валидация,
   проверка `tasks.md`, тесты и deploy. В Plane указываются change, коммиты,
   изменения и способ проверки. Change остаётся активным — не архивировать.
7. **Закрытие.** Только после перевода пользователем в «Задача закрыта»
   выполняется `openspec archive <change-id> --yes`: delta попадает в
   `openspec/specs/`, change — в `openspec/changes/archive/`. Результат
   коммитится и пушится, затем агент останавливается.

## Правила качества

- Спецификация, код и тесты одной задачи попадают в один логический результат;
  чужие незакоммиченные изменения не затираются.
- Каждое требование имеет проверяемый сценарий; критичные сценарии получают
  автотест. Нельзя закрывать задачу, если реализация расходится со spec.
- `openspec validate --all --strict --json` запускается перед финальным
  коммитом спецификаций. Команды archive без `--yes` в фоне не использовать.
- Ретроспективное описание уже существующей системы — отдельный этап:
  сначала базовые `openspec/specs/<capability>/spec.md`, без изменения кода.
