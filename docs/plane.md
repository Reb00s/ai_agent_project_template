# Plane — управление задачами проекта

Task manager [Plane](https://plane.so) (self-hosted в локальной сети).
Подключается к агенту по запросу пользователя через MCP-сервер `plane`
(пакет `plane-mcp-server` с PyPI, запуск через uvx).

Имена проекта, воркспейса и адрес сервера **конкретной установки не
зафиксированы в репозитории** — их задаёт пользователь при подключении
(плейсхолдеры ниже). Токен доступа в git не коммитить никогда.

## Подключение проекта (протокол)

1. **Запрос.** Пользователь просит подключить проект к Plane.
2. **Доступность.** Агент проверяет, что Plane доступен в локальной сети
   (`scripts/plane_connect.py`, шаг 1).
3. **Данные подключения.** Если сервер доступен, агент запрашивает у
   пользователя: токен доступа (X-Api-Key) и имя существующего проекта в
   Plane. Значения передаются скриптам через окружение:
   `PLANE_BASE_URL` (например `http://<адрес-сервера>`),
   `PLANE_WORKSPACE_SLUG` (короткое имя воркспейса), `PLANE_API_KEY`,
   `PLANE_PROJECT_NAME`.
4. **Статусная модель.** При синхронизации агент сверяет статусы проекта с
   эталоном (ниже). Если модель отличается — приводит к эталону
   (недостающие состояния создаются). Все три хелпера используют одни и
   те же переменные окружения.
5. **Вопрос об опросе.** По завершении подключения агент спрашивает
   пользователя, запускать ли в текущей сессии опрос очереди. Если «да» —
   агент создаёт cron-задачу внутри живой сессии Kimi Code
   (`CronCreate`, recurring `* * * * *` — каждую минуту), промпт которой
   оркестрирует очередь по правилам ниже: проверяет свободные слоты
   субагентов и отдаёт задачи в работу. Задача живёт, пока жива сессия;
   при её закрытии опрос прекращается — пересоздаётся только по новому
   запросу. Если «нет» — опрос не запускается.
6. **Лимит субагентов.** При подключении пользователь задаёт максимум
   одновременно работающих субагентов (по умолчанию 3). Значение
   сохраняется в `~/.kimi-code/plane_agents.json` (`{"agents_limit": N}`) —
   файл локальный, в git не коммитить. Меняется вручную или по запросу
   пользователя.
7. **Финал.** При успешных шагах 1–6 агент создаёт тестовую задачу в бэклоге
   (`scripts/plane_connect.py`, тестовое описание) — на этом подключение
   завершено.

## MCP-сервер

Конфиг (`~/.kimi-code/mcp.json`):

```json
{
  "mcpServers": {
    "plane": {
      "command": "$HOME/.local/bin/uvx",
      "args": ["plane-mcp-server", "stdio"],
      "env": {
        "PLANE_API_KEY": "<plane_api_… — из защищённого хранилища>",
        "PLANE_WORKSPACE_SLUG": "<WORKSPACE_SLUG>",
        "PLANE_BASE_URL": "http://<адрес-сервера>"
      }
    }
  }
}
```

Установка окружения: `curl -LsSf https://astral.sh/uv/install.sh | sh`
(ставит `uv`/`uvx` в `~/.local/bin`). Инструменты в сессии: `mcp__plane__*`
(workitem, cycle, module, project, label, member, page, work_log,
get_pql_reference…).

## Эталонная статусная модель

| Статус | Группа | Кто переводит |
|---|---|---|
| Задача запланирована | backlog | пользователь/планирование |
| Задача в анализе | unstarted | пользователь |
| **Задача в работе** | started | пользователь (старт для агента) |
| **Задача в доработке** | started | пользователь (возврат с замечаниями) |
| **Задача на тестировании** | started | **агент** (после выполнения/доработки) |
| Задача закрыта | completed | пользователь (после успешной проверки) |
| Задача отменена | cancelled | пользователь |

## Правила работы с задачами (обязательные)

1. **Опрос.** Каждую минуту cron-задача внутри живой сессии проверяет
   Plane: есть ли задачи в статусах «Задача в работе» и «Задача в
   доработке». Создаётся только после согласия пользователя (шаг 5
   протокола подключения) и умирает вместе с сессией.
2. **Исполнители — субагенты.** Все задачи выполняют субагенты
   (фоновые агенты Kimi Code). Оркестратор (ход cron-задачи) сам код не
   пишет: он считает свободные слоты = `agents_limit`
   (`~/.kimi-code/plane_agents.json`, по умолчанию 3) минус число
   активных фоновых задач с пометкой «Plane-агент: …» и, пока есть слоты
   и задачи в очереди, отдаёт очередную задачу следующему субагенту.
   Несколько задач запускаются параллельно (AgentSwarm — по числу задач).
3. **Порядок выбора.** Сначала — статус: любая «Задача в доработке»
   берётся раньше любой «Задача в работе». Внутри одного статуса —
   приоритет задачи (urgent → high → medium → low → none), затем — дата
   последнего изменения статуса (раньше изменённая берётся первой);
   при равенстве — любая. Готовый хелпер:
   `python3 scripts/plane_next_task.py --limit <слоты> --json`.
4. **Полный цикл субагентом.** Каждый субагент выполняет свою задачу
   целиком: читает описание и комментарии issue → правит код в репозитории
   приложения → прогоняет тесты → выкатывает на контур → проверяет →
   сдаёт в Plane по правилам 5–9. В описание фоновой задачи субагента —
   ровно «Plane-агент: <идентификатор> — <название>», по этой пометке
   оркестратор считает занятые слоты.
5. **Сдача в тестирование.** После выполнения субагент переводит задачу
   в «Задача на тестировании» и дополняет карточку контекстом для будущих
   доработок: коммит(ы), что изменено, как проверять (ссылки на контур,
   учётки-тесты, замечания по граничным случаям).
6. **Замечания.** Пользователь при тестировании оставляет замечания
   **комментариями** в карточке задачи.
7. **Возврат на доработку.** После проверки пользователь сам переводит задачу
   в «Задача в доработке».
8. **Доработка.** Субагент устраняет замечания и **по каждому комментарию
   кратко отписывается, что сделано** (ответным комментарием), затем
   переводит задачу в «Задача на тестировании».
9. **Цикл.** Пункты 6–8 повторяются, пока замечания не устранены и
   пользователь не переведёт задачу в «Задача закрыта». Закрывает задачу
   только пользователь.

## Скрипты

- `scripts/plane_connect.py` — подключение по протоколу выше (доступность →
  статусная модель → тестовая задача). `--dry-run` — только проверки.
- `scripts/plane_next_task.py` — следующие задачи для взятия в работу
  (правило 3). `--limit N --json` — до N задач машиночитаемым массивом
  (для оркестрации субагентами); без флагов — одна задача текстом.
- `scripts/plane_sync.py` — зеркалирует чекбоксы `tasks/current.md` и
  `tasks/backlog.md` в Plane: создаёт отсутствующие issues, приводит статусы
  (`[ ]` → «Задача в анализе», `[x]` → «Задача закрыта»). Сопоставление по
  имени, описания созданных issues в Plane руками править можно. `--dry-run`,
  `--root`.

Все скрипты читают `PLANE_BASE_URL`, `PLANE_WORKSPACE_SLUG`, `PLANE_API_KEY`,
`PLANE_PROJECT_NAME` из окружения — дефолтов в коде нет, значения выдаёт
пользователь при подключении.

Основной поток задач ведётся в Plane; `tasks/` — для локального планирования
и долгосрочного бэклога проекта-шаблона.
