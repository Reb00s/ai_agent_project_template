# Plane — управление задачами проекта

Task manager [Plane](https://plane.so) (self-hosted в локальной сети).
Подключается к агенту по запросу пользователя через MCP-сервер `plane`
(пакет `plane-mcp-server` с PyPI, запуск через uvx).

Имена проекта, воркспейса и адрес сервера **конкретной установки не
зафиксированы в репозитории** — их задаёт пользователь при подключении
(плейсхолдеры ниже). Токен доступа в git не коммитить никогда.

## Подключение проекта (протокол)

1. **Запрос.** Пользователь просит подключить проект к Plane.
2. **Доступность.** Агент проверяет, что Plane доступен в локальной сети
   (`scripts/plane_connect.py`, шаг 1).
3. **Данные подключения.** Если сервер доступен, агент запрашивает у
   пользователя: токен доступа (X-Api-Key) и имя существующего проекта в
   Plane. Значения передаются скриптам через окружение:
   `PLANE_BASE_URL` (например `http://<адрес-сервера>`),
   `PLANE_WORKSPACE_SLUG` (короткое имя воркспейса), `PLANE_API_KEY`,
   `PLANE_PROJECT_NAME`.
4. **Статусная модель.** При синхронизации агент сверяет статусы проекта с
   эталоном (ниже). Если модель отличается — приводит к эталону
   (недостающие состояния создаются). Все три хелпера используют одни и
   те же переменные окружения.
5. **Финал.** При успешных шагах 1–4 агент создаёт тестовую задачу в бэклоге
   (`scripts/plane_connect.py`, тестовое описание) — на этом подключение
   завершено.

## MCP-сервер

Конфиг (`~/.kimi-code/mcp.json`):

```json
{
  "mcpServers": {
    "plane": {
      "command": "$HOME/.local/bin/uvx",
      "args": ["plane-mcp-server", "stdio"],
      "env": {
        "PLANE_API_KEY": "<plane_api_… — из защищённого хранилища>",
        "PLANE_WORKSPACE_SLUG": "<WORKSPACE_SLUG>",
        "PLANE_BASE_URL": "http://<адрес-сервера>"
      }
    }
  }
}
```

Установка окружения: `curl -LsSf https://astral.sh/uv/install.sh | sh`
(ставит `uv`/`uvx` в `~/.local/bin`). Инструменты в сессии: `mcp__plane__*`
(workitem, cycle, module, project, label, member, page, work_log,
get_pql_reference…).

## Эталонная статусная модель

| Статус | Группа | Кто переводит |
|---|---|---|
| Задача запланирована | backlog | пользователь/планирование |
| Задача в анализе | unstarted | пользователь |
| **Задача в работе** | started | пользователь (старт для агента) |
| **Задача в доработке** | started | пользователь (возврат с замечаниями) |
| **Задача на тестировании** | started | **агент** (после выполнения/доработки) |
| Задача закрыта | completed | пользователь (после успешной проверки) |
| Задача отменена | cancelled | пользователь |

## Правила работы с задачами (обязательные)

1. **Опрос.** Каждые 5 минут агент проверяет Plane: есть ли задачи в статусах
   «Задача в работе» и «Задача в доработке».
2. **Взятие в работу.** Найденные задачи агент берёт в работу.
3. **Порядок выбора.** Сначала — приоритет задачи (urgent → high → medium →
   low → none), затем — дата последнего изменения статуса (раньше изменённая
   берётся первой); при равенстве — любая. Готовый хелпер:
   `python3 scripts/plane_next_task.py`.
4. **Сдача в тестирование.** После выполнения агент переводит задачу в «Задача
   в тестировании» и дополняет карточку контекстом для будущих доработок:
   коммит(ы), что изменено, как проверять (ссылки на контур, учётки-тесты,
   замечания по граничным случаям).
5. **Замечания.** Пользователь при тестировании оставляет замечания
   **комментариями** в карточке задачи.
6. **Возврат на доработку.** После проверки пользователь сам переводит задачу
   в «Задача в доработке».
7. **Доработка.** Агент устраняет замечания и **по каждому комментарию кратко
   отписывается, что сделано** (ответным комментарием), затем переводит задачу
   в «Задача на тестировании».
8. **Цикл.** Пункты 5–7 повторяются, пока замечания не устранены и
   пользователь не переведёт задачу в «Задача закрыта». Закрывает задачу
   только пользователь.

## Скрипты

- `scripts/plane_connect.py` — подключение по протоколу выше (доступность →
  статусная модель → тестовая задача). `--dry-run` — только проверки.
- `scripts/plane_next_task.py` — следующая задача для взятия в работу
  (правило 3).
- `scripts/plane_sync.py` — зеркалирует чекбоксы `tasks/current.md` и
  `tasks/backlog.md` в Plane: создаёт отсутствующие issues, приводит статусы
  (`[ ]` → «Задача в анализе», `[x]` → «Задача закрыта»). Сопоставление по
  имени, описания созданных issues в Plane руками править можно. `--dry-run`,
  `--root`.

Все скрипты читают `PLANE_BASE_URL`, `PLANE_WORKSPACE_SLUG`, `PLANE_API_KEY`,
`PLANE_PROJECT_NAME` из окружения — дефолтов в коде нет, значения выдаёт
пользователь при подключении.

Основной поток задач ведётся в Plane; `tasks/` — для локального планирования
и долгосрочного бэклога проекта-шаблона.
